# DAV implementation research

Checked 2026-10-17 against primary specifications and official upstream source. No live server requests, mailbox tests, or mutations were performed. Recommendations below are implementation decisions, not claims that a particular deployed server supports every feature.

## Discovery and collection enumeration

1. Start with the configured HTTPS DAV context URL. If doing standards-based bootstrapping, resolve `/.well-known/caldav` or `/.well-known/carddav` redirects to that context; well-known resources are redirect stubs, not DAV service roots. A well-known request may require authentication before returning its redirect. [RFC 6764 §5](https://www.rfc-editor.org/rfc/rfc6764.html#section-5)
2. `PROPFIND` the context with `Depth: 0`, explicitly requesting `{DAV:}current-user-principal`. Its `href` identifies the authenticated principal; `unauthenticated` means authentication has not succeeded. [RFC 5397 §3](https://www.rfc-editor.org/rfc/rfc5397.html#section-3)
3. `PROPFIND` that principal with `Depth: 0` for `{urn:ietf:params:xml:ns:caldav}calendar-home-set` and `{urn:ietf:params:xml:ns:carddav}addressbook-home-set`. Each can contain multiple home URLs; a home may itself be a calendar/address book or contain descendant collections. [RFC 4791 §6.2.1](https://www.rfc-editor.org/rfc/rfc4791.html#section-6.2.1), [RFC 6352 §7.1.1](https://www.rfc-editor.org/rfc/rfc6352.html#section-7.1.1)
4. Enumerate each home using `PROPFIND Depth: 1`, requesting `resourcetype`, `displayname`, `supported-report-set`, and relevant capabilities. Classify by namespace URI plus local name, never XML prefix. A calendar has CalDAV `calendar`; an address book has CardDAV `addressbook` in its `resourcetype`. Use `supported-calendar-component-set` to distinguish VEVENT calendars from task-only calendars. [RFC 4791 §§4.2, 5.2.3](https://www.rfc-editor.org/rfc/rfc4791.html#section-4.2), [RFC 6352 §5.2](https://www.rfc-editor.org/rfc/rfc6352.html#section-5.2)

Always set PROPFIND depth; omitted depth can imply infinity. Request named properties because `allprop` excludes some live properties. Parse every `response` and `propstat` status: HTTP 207 alone is not success for every member/property. Resolve returned hrefs against the response/request URL without decoding/re-encoding away resource identity; URLs may be absolute or paths. Disable DTD/entity expansion and external entity resolution. [RFC 4918 §§8.3, 9.1, 13, 20.6](https://www.rfc-editor.org/rfc/rfc4918.html#section-9.1)

## Reading and conditional writes

CalDAV `REPORT calendar-query` with `Depth: 1` filters objects, for example VCALENDAR → VEVENT with an optional time range. Request `DAV:getetag` and `calendar-data`. `calendar-multiget` requests explicit hrefs and retrieves their ETags and complete payloads. A time-window query is a view; its missing rows do not prove server deletion. Preserve the full resource, including recurrence instances and timezone components, when editing. Calendar resources cannot contain an iCalendar METHOD property. [RFC 4791 §§4.1, 7.8–7.9](https://www.rfc-editor.org/rfc/rfc4791.html#section-7.8)

CardDAV offers `addressbook-query` with filters and `addressbook-multiget` with explicit hrefs; request `DAV:getetag` plus `address-data`. New contact resources use PUT to an unmapped child URL with `If-None-Match: *`; updates should send `If-Match` with the prior ETag and resolve conflicts before retrying. Preserve unedited vCard fields rather than reconstructing a partial card. [RFC 6352 §§6.3.2, 8.6–8.7, 9.1–9.2](https://www.rfc-editor.org/rfc/rfc6352.html#section-8.7)

Use unique child `.ics`/`.vcf` URLs for creates; retain server href separately from UID. Send exact strong ETags, including quotes, in `If-Match` for PUT and DELETE; a failed condition normally yields 412. Never retry unconditionally. If a PUT transforms stored content, its success response cannot provide a validator for unchanged submitted bytes: re-fetch the stored payload and ETag when needed. [RFC 4791 §§5.3.2–5.3.4](https://www.rfc-editor.org/rfc/rfc4791.html#section-5.3.2), [RFC 9110 §§9.3.4, 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

## Deletion reconciliation and incremental sync

Check collection `supported-report-set` before relying on `sync-collection`. Send REPORT with `Depth: 0`, a `sync-token` (empty for initial state), `sync-level` = `1`, and requested `getetag`. Persist tokens as opaque per-collection values. Changed members contain propstat; removed members contain a direct response-level 404 with no propstat. A property-level 404 is not a deleted object. Invalid-token errors require a complete resync. A collection-level 507 with a returned token can mean a partial page: continue from that token. [RFC 6578 §§3.2–3.7](https://www.rfc-editor.org/rfc/rfc6578.html#section-3.2)

Implementation recommendation: apply changes and advance the token atomically only after returned payloads are durably processed. Without sync support, obtain a complete unfiltered href/ETag inventory with PROPFIND Depth:1, fetch new/changed objects, and remove cached members absent from that successful inventory. Never prune from a failed, truncated, permission-denied, or time-filtered response. After DELETE success, reconcile local state; a lost response requires re-reading before deciding whether retry is necessary. This follows the complete inventory/ETag comparison approach illustrated by [RFC 4791 §8.2.1](https://www.rfc-editor.org/rfc/rfc4791.html#section-8.2.1) and [RFC 6578 Appendix B](https://www.rfc-editor.org/rfc/rfc6578.html#appendix-B).

## Preventing invitations and scheduling messages

PUT and DELETE can trigger implicit scheduling. RFC 6638 defaults `SCHEDULE-AGENT` to `SERVER`; organiser create/update/delete may generate REQUEST/CANCEL messages. `SCHEDULE-AGENT=NONE` requests no scheduling for the corresponding party. `Schedule-Reply: F` suppresses an attendee's deletion reply; it is not a universal suppression header for organiser cancellation or PUT. [RFC 6638 §§3.2.1, 7.1, 8.1](https://www.rfc-editor.org/rfc/rfc6638.html#section-7.1)

Implementation decision for a strict no-send phase: create personal VEVENTs without ORGANIZER or ATTENDEE, reject supplied scheduling fields, and block update/delete of existing resources containing either property anywhere in any recurrence component. Do not remove attendees from a meeting as a supposed safe workaround: removal can itself trigger scheduling. Do not POST to scheduling outboxes or submit iTIP/iMIP. Explicitly gate future meeting support separately. This conservative policy avoids depending on unverified server-specific suppression behavior. [RFC 6638 §§3.2.1.2–3.2.1.3](https://www.rfc-editor.org/rfc/rfc6638.html#section-3.2.1.2)

This matters on grommunio: upstream `server.php` installs scheduling and iMIP plugins, and the iMIP implementation calls `mapi_message_submitmessage`. These are source observations, not deployed-version verification. [grommunio server.php](https://github.com/grommunio/grommunio-dav/blob/master/server.php), [GrommunioIMipPlugin.php](https://github.com/grommunio/grommunio-dav/blob/master/lib/GrommunioIMipPlugin.php)

## Authentication, redirects, and endpoint paths

Use TLS with certificate verification. Bind credentials to the explicitly configured origin (scheme, host, effective port). Implement bounded manual redirects and validate every Location and DAV href before an authenticated request; reject off-origin URLs, HTTPS downgrade, userinfo URLs, and unexpected ports. Treat discovery redirection as endpoint resolution followed by a fresh DAV request; do not permit an HTTP library to silently change PROPFIND/REPORT into GET. Strip credentials on any origin change; support an alternate origin only through explicit configuration. These are conservative implementation policies informed by [RFC 9110 §§11.5, 15.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4) and [RFC 6764 §5](https://www.rfc-editor.org/rfc/rfc6764.html#section-5).

Official grommunio setup documents `/dav/` as context and `/dav/calendars/<user>/Calendar/` as an example calendar URL, with account username/password. Configuration defines `DAV_ROOT_URI` as `/dav/`, while upstream server code uses Basic authentication unless an Apache authentication backend is configured. Calendar names/user segments are examples, not stable identities: discover actual hrefs. [Official DAV README](https://github.com/grommunio/grommunio-dav#usage), [config.php](https://github.com/grommunio/grommunio-dav/blob/master/config.php), [server.php](https://github.com/grommunio/grommunio-dav/blob/master/server.php)

Upstream principals use `principals/<username>`. The custom address book root inherits Sabre's AddressBookRoot; its plugin maps the home to `addressbooks/<principalId>`, implying `/dav/addressbooks/<user>/` under the default context. This is source-derived, not a verified deployed path. Do not hard-code a personal Contacts collection or assume every discovered address book is writable (a GAL may also be exposed). Discover the addressbook-home-set and individual collection hrefs. [PrincipalsBackend.php](https://github.com/grommunio/grommunio-dav/blob/master/lib/PrincipalsBackend.php), [GalAddressBookRoot.php](https://github.com/grommunio/grommunio-dav/blob/master/lib/GalAddressBookRoot.php), [Sabre CardDAV Plugin](https://github.com/sabre-io/dav/blob/4.4.0/lib/CardDAV/Plugin.php), [official client setup](https://docs.grommunio.com/user/groupware/)
